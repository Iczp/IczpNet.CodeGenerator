# IczpNet Code Generator 设计说明

## 1. 定位

`IczpNet.CodeGenerator` 是面向 ABP vNext DDD 项目的本地 C# 代码生成器。它以领域实体为事实来源，通过 Roslyn 语义分析、项目约定和可版本化模板，生成 Contracts、Application、Domain、EntityFrameworkCore 相关代码。

当前目标平台为 **.NET 10 + ABP 10.6.1**。`IczpNet.Cms\aspnet-core` 是首个验收目标；其 `Volo.Abp.*` 包版本为 `10.6.1`。

旧 `node-code-gen` 是历史参考，不是新实现的运行时依赖。它只提供应覆盖的模板功能清单：

- DTO、Create/Update Input、GetList Input；
- Repository、Domain Manager、AppService；
- Validator、Mapper；
- Permission、Localization；
- OpenAPI TypeScript Client（独立可选功能）。

新版不迁移旧代码中的 `IczpNet.Invoicing` 命名空间、固定目录、硬编码基类、文本替换或直接覆盖文件的行为。

## 2. 核心原则

1. **实体优先**：实体源代码及其编译语义是类型、可空性、继承、特性和领域行为的唯一事实来源。
2. **模板功能可借鉴，平台实现不照搬**：旧版模板定义“要生成哪些层”，ABP 10.6.1 Profile 定义“这些层如何生成”。
3. **版本隔离**：中立生成模型不引用某个 ABP API；所有 ABP API、using、基类和注册方式由版本 Profile/适配层决定。
4. **安全生成**：先得到计划和 Diff，再写入；只能覆盖带机器头且状态可验证的生成文件；手写扩展文件只首建。
5. **配置最小化**：Profile 提供默认规则，实体 Descriptor 仅保存例外，不重复保存 Roslyn 可分析的信息。
6. **可验证**：生成必须在隔离副本中恢复、构建并验证，通过后才写入目标项目。

## 3. 总体架构

```text
ABP Domain entity source
  -> Roslyn semantic analysis
  -> EntityModel
  -> Convention + Descriptor
  -> version-neutral GenerationModel
  -> selected ABP Profile / adapter (abp-10.6)
  -> Scriban templates
  -> GenerationPlan + Diff
  -> isolated build validation
  -> guarded write / recovery journal
```

CLI、Web UI 和未来 IDE 插件仅负责输入输出，统一调用 Core 的分析、计划、验证和写入服务。

## 4. ABP 版本策略

### 4.1 当前基线：`abp-10.6`

默认 Profile 为 `abp-10.6`，针对 ABP `10.6.1` 验证。它负责：

- ABP Repository、Application Service、Permission、EF Core API 的具体用法；
- 生成文件目录、命名、命名空间与项目层映射；
- 审计、多租户、软删除、并发控制的默认规则；
- DTO、查询输入、验证、映射、权限和本地化的模板选择。

生成器在分析项目布局时读取目标项目的 `Volo.Abp.*` PackageReference 版本：

- `10.6.x` 默认选用 `abp-10.6`；
- 已知兼容的后续补丁版本可复用该 Profile；
- 主版本不匹配或未注册兼容范围时停止生成并明确提示；
- 不允许因为未识别版本而静默套用不确定的 ABP API。

### 4.2 后续 ABP 版本

当 ABP 的生成相关 API 或约定出现破坏性变化时，新增 `abp-<major>` Profile 与少量对应适配器，例如 `abp-11`。不得在实体分析模型或通用模板中增加版本判断。

```text
EntityModel / GenerationModel    不绑定 ABP 版本
abp-10.6 Profile                 当前生产基线
abp-11 Profile                   未来并存实现
```

这样既能为旧目标重现已有输出，也能逐步支持新版本。

## 5. 输入模型

### 5.1 `EntityModel`：Roslyn 分析结果

扫描器必须基于 `MSBuildWorkspace`/Compilation 的语义模型，而不是只做语法文本匹配。每个实体至少提取：

- 完整名称、项目、模块/特性目录、基类及主键；
- ABP 能力：AggregateRoot、审计类型、`IMultiTenant`、软删除、并发戳、额外属性；
- 属性：CLR 类型、可空性、集合/导航关系、枚举、访问器可见性、XML 文档；
- 数据标注与约束：`Required`、`StringLength`、`MaxLength`、范围、正则、默认值；
- 构造函数及参数、领域更新方法及参数；
- 由符号分析得出的系统维护字段和不可安全写入字段。

`EntityModel` 是只读事实模型；它不包含用户选择。

### 5.2 `GenerationDescriptor`：实体级例外

Descriptor 只记录与默认规则不同的意图：

- 启用的功能模块；
- CRUD 操作、权限和查询规则；
- 字段在 DTO/Create/Update/List/Detail 中的曝光覆盖；
- 验证、默认值、显示名与本地化键的覆盖；
- 构造和更新行为无法安全推导时的显式绑定。

Descriptor 必须包含实体结构指纹。指纹变化后，生成器展示迁移提示并阻止未确认的写入。

### 5.3 `GenerationModel`：模板唯一输入

将 `EntityModel + Convention + Descriptor + Profile` 合并成模板可直接使用的模型。模板不得自行读取实体源码、JSON、任意本机路径或执行命令。

## 6. 模板功能族

旧 Node 版的功能范围被归纳为以下可选生成模块；具体输出由 `abp-10.6` Profile 决定。

| 模块 | 主要输出 | 所有权 |
| --- | --- | --- |
| Contracts DTO | `Dto`、`DetailDto`、`CreateInput`、`UpdateInput`、`GetListInput` | 完全生成 `.g.cs` |
| Domain | Repository 接口、可选 Manager 接口/实现 | 生成基类或受管文件 |
| Application | AppService 基类、接口、Validator、Mapper | 基类完全生成；扩展类仅首建 |
| EF Core | Repository 基类、实体配置基类、DbContext 注册 | 基类完全生成；注册受控修改 |
| Authorization | Permission 常量、Permission Definition 注册 | 完全生成或受控修改 |
| Localization | 资源键和值 | 受控 JSON 修改 |
| HTTP Client | 从 OpenAPI 文档生成 TypeScript Client | 独立命令，不与后端写入耦合 |

DTO 可按 Profile 选择平铺形式或 `SampleDto -> Dto -> DetailDto` 继承层次；不要把旧版的继承结构视为唯一方案。

## 7. 智能默认规则

`abp-10.6` Profile 必须将实体元数据转换为可解释的默认值：

- `string`：DTO/Create/Update 默认暴露；列表默认 contains 过滤；长度约束进入验证与 EF 配置。
- 数字、`DateTime`、`DateTimeOffset`：列表默认范围过滤；可按配置排序。
- `bool`、`Guid`、enum：列表默认 equals 过滤；enum 自动保留强类型。
- 导航和集合：默认不写入 Create/Update；由 Descriptor 明确选择 DTO 投影或关联操作。
- 审计、多租户、软删除、并发等系统字段：不进入写入 Input；是否输出到 Detail DTO 由 Profile 决定。
- `protected set` 不等于不可更新；Create/Update 必须优先依据构造函数和领域方法，无法推导时要求 Descriptor 明确配置。

生成器的职责是提供可靠默认值和可编辑预览，而非猜测领域业务规则。

## 8. 输出与写入策略

| 输出类别 | 策略 |
| --- | --- |
| 完全生成文件 | 使用 `// <auto-generated />`，可安全更新 |
| 手写扩展点 | 仅首次创建，后续始终 Skip |
| 既有基础设施文件 | 仅以唯一 Roslyn 锚点进行受控修改；锚点缺失或不唯一即 Conflict |
| 本地化 JSON | 解析并保持格式/键唯一性；禁止原始字符串插入 |

一次生成遵循：

```text
Analyze -> Plan -> Preview/Diff -> isolated build -> guarded write -> journal/state update
```

写入前重新创建计划、检查哈希和冲突。中断后通过持久化 journal 恢复。任何验证失败都不能改变目标工作区。

## 9. 目录与配置

```text
.codegen/
  config.json                         # 默认 Profile、解决方案信息
  profiles/
    abp-10.6.json
  entities/
    Article.codegen.yaml
  state/
    Article.state.json

templates/
  common/                              # 与 ABP 版本无关的片段
  abp-10.6/                            # ABP 10.6.1 模板族
    contracts/
    domain/
    application/
    entity-framework-core/
    authorization/
```

Profile、模板和 Descriptor 必须提交 Git。状态文件是否提交由团队策略决定，但 CI 必须能够发现实体改变而未重新生成的情况。

## 10. 命令与验证

```text
abpgen init [--profile abp-10.6]
abpgen entities [--project <domain-project>] [--json]
abpgen inspect <entity> [--json]
abpgen init-entity <entity>
abpgen plan <entity>
abpgen generate <entity> [--dry-run]
abpgen validate [entity]
abpgen recover
abpgen openapi generate [--input <url-or-file>]
```

`plan` 和 `generate --dry-run` 绝不写入。`generate` 只有在预检、隔离构建和冲突检查通过后写入。Web UI 复用完全相同的服务与计划模型。

## 11. 实施顺序

1. 将 ABP 版本检测和 `abp-10.6` Profile 加入项目配置与验证。
2. 将 Roslyn 扫描从语法级扩展为语义级，丰富 `EntityModel`。
3. 把当前硬编码的 C# 输出迁至 `templates/abp-10.6`，保持既有安全写入流程。
4. 以旧版模板功能清单补齐 Contracts、Repository、Manager、AppService、Validator、Mapper、Permission、Localization。
5. 用 CMS 的 `Article` 与 `CatalogEntry` 覆盖 Guid/int、enum、可空字段、审计实体和 CRUD 差异的集成测试。
6. 在后续 ABP 大版本发布且出现相关 API 变化时，再新增对应 Profile；不提前猜测其 API。

## 12. 非目标

- 不生成或覆写领域实体及领域业务规则；
- 不把旧 `node-code-gen` 作为生产依赖；
- 不在未知 ABP 大版本上“尽力生成”；
- 不用字符串替换覆盖手写代码；
- 不在没有明确需求时修改 `IczpNet.Cms` 的手写业务代码。
